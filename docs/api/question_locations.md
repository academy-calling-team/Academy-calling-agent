# 질문별 위치와 통화 날짜 문맥

## 문의 입력

`POST /api/inquiries`의 선택적 `locations`는 요청한 질문 중 `shuttle`(등원 출발지), `pickup`(하원 목적지)만 가진다. 각 위치의 kind는 `집 근처`·`학교`·`다른 학원`, name은 앞뒤 공백을 제거한 1~100자다. 선택하지 않은 질문의 위치, 잘못된 종류·공백만 있는 장소명은 422다.

```json
{
  "inquirer_id": "authenticated-owner",
  "academy_id": "selected-academy",
  "student": {"grade": "M2", "subject": "MATH", "level": "MID"},
  "question_codes": ["shuttle", "pickup", "vacancy"],
  "locations": {
    "shuttle": {"kind": "학교", "name": "침산초등학교"},
    "pickup": {"kind": "집 근처", "name": "침산네거리"}
  }
}
```

웹 중계는 locations를 보존하고 inquirer_id는 인증 세션에서 지정한다. 학생 region은 API에서 생략/null을 허용하며 워커는 ‘거주 지역 미입력’으로 처리한다. 현재 웹의 기존 지역 선택은 유지한다.

웹 화면은 통학 차량/픽업을 선택한 경우에만 해당 위치 입력을 표시한다. 위치 미입력도 가능하며 종류를 골랐다면 장소명이 필요하다. 질문 선택을 해제하면 해당 위치도 제거한다. 응답을 받지 못해 다시 접속했을 때 대기 중 문의의 위치를 복원한다.

## 저장·조회와 기존 요청 호환

- 질문별 위치는 `w5_questions.location_kind/location_name`의 nullable 열에 저장한다.
- 상세 `questions[]`와 발신 `questions[]`는 위치가 있을 때만 `location: {kind, name}`을 포함한다. 위치 없는 기존 질문에는 키를 추가하지 않는다.
- 상세에 `created_at`을 반환하고 입력한 등원 출발지/하원 목적지를 화면에 표시한다.
- locations 생략·null·빈 객체는 위치 없는 같은 입력으로 취급해 기존 문의의 payload_hash와 호환된다. 같은 요청 키·같은 입력은 기존 문의를 반환하고, 실제 위치가 바뀌면 409를 유지한다.
- 음성 접수 저장 시 새 선택 필드가 없는 요청은 과거 payload 형식을 유지해 같은 call_id의 기존 접수 재전송을 중복으로 인식한다.
- 위치는 질문의 입력 문맥이다. 결과 `answers[]`에는 question_id/question_code와 기존 결과 필드만 보낸다. 입력의 location을 답변에 펼쳐 넣지 않는다.

## 시각의 의미

발신을 예약할 때 다음 문맥을 발신 payload에 고정 저장한다. 워커 전달 재시도에서는 동일 본문을 재사용한다.

```json
{
  "time_context": {
    "inquiry_created_at": "2026-11-14T04:00:00+00:00",
    "dispatch_requested_at": "2026-11-15T05:00:00+00:00",
    "timezone": "Asia/Seoul"
  }
}
```

- inquiry_created_at: 문의 접수 시각.
- dispatch_requested_at: 큐에서 해당 발신을 예약한 시각. 실제 학원이 전화를 받은 시각이 아니다.
- timezone: 상대 날짜를 해석할 시간대인 Asia/Seoul.
- call_started_at: 실제 음성 워커가 제공업체에 발신을 요청하기 시작한 시각. 워커의 지시문·판정 단계에서 추가하는 내부 문맥이며 클라이언트가 지정하지 않는다. 기존 ProviderCalls.created_at 저장을 재사용해 재시작 후에도 같은 기준을 쓴다.

‘오늘·내일·이번 주·금요일’은 발신 시작 시점의 한국 시간으로 확인한다. 접수일이 전날이어도 이를 통화일로 사용하지 않는다. 통화 지시문과 LLM 판정 입력에는 기준 시각을 함께 전달하고, 실제 연결 결과의 notes에도 날짜 해석 기준을 남긴다. 과거 통화의 기준 시각이 없으면 새 날짜를 임의로 확정하지 않는다. 상대 시간 표현을 일괄 날짜로 변환하거나 상담 예약을 자동 확정하는 기능은 추가하지 않는다.

위치가 지정되면 지시문은 등원은 ‘입력 장소→학원’, 하원은 ‘학원→입력 장소’로 묻는다. LLM 판정에도 요청 위치와 방향을 전달한다. 6종 판정 상태 신설·새 폴백·실제 발신 허용 범위 변경은 포함하지 않는다.

실제 공유 워커의 요청 스키마는 `call_request_json_schema.json`, 백엔드 입력과 결과는 `openapi.json`·`result_json_schema.json`에서 확인한다.

검증은 문맥 전달·기준 시각 보존·계약 왕복까지다. 실제 모델의 장소·상대 날짜 해석 정확도는 같은 시험 세트로 별도 평가해야 하며, 이번 작업에서 외부 LLM 호출이나 실통화를 수행하지 않는다.

## DB 적용·병합·배포 순서

1. 최신 PR 자동 검사 통과와 사용자 검토를 확인한다. 현재 PR 업로드는 병합·운영 변경 완료를 의미하지 않는다.
2. 공동 DB를 사전 백업하고 복구 자료를 확인한다.
3. 대상 DB 선택 후 `docs/database/migrations/20261115_question_locations.sql`을 실행한다. 두 nullable 열만 추가하며 기존 질문은 유지한다. 일부 열만 적용된 경우와 반복 실행도 허용한다.
4. 두 열의 타입·NULL, 기존 질문 행 수·기존 답변 보존을 확인한다. API/워커 이미지를 서로 다른 계약 상태로 운영하지 않도록 함께 반영한다.
5. 승인된 병합·배포 후 버전·DB/큐 상태와 지정 목업 학원에서 접수→발신 요청→결과 조회를 확인한다. 실제 발신은 기존 별도 허용 정책을 따른다.

신규 열 적용 뒤 이전 이미지로 복구할 때 두 nullable 열은 남겨도 된다. 복구 중 위치 데이터를 임의 삭제하거나 열을 제거하지 않는다. 이번 PR 작업에서 공동 DB 적용·main 병합·운영 배포·실통화는 수행하지 않는다.
