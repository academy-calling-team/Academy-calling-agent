# 공동 서버 운영과 배포

## 현재 구성

기존EC2에서team8-shared-api(0.4.0),team8-shared-worker(음성팀목업),team8-shared-queue(HTTP워커연결)가동작한다. 기존team8_dev와team8-fe-dev-redis의DB2를사용한다. 프론트시험용DB1처리기와분리됐다.

워커와큐는API의네트워크공간을공유한다. 큐→http://127.0.0.1:18780,워커→http://127.0.0.1:18771로내부통신한다. 공개/shared/internal과/shared/ops는차단유지한다. 외부HTTPS문서경로는/shared/docs이다.

워커접수SQLite는team8-shared-worker-receipts볼륨에보존한다. 실행사용자UID10001의쓰기권한을보장해야한다. DB/API스키마는초기화하지않는다. 설정은/opt/team8-shared-api/runtime의root전용파일이며로그·Git·팀공유문서에비밀값을복사하지않는다.

## 관리 권한과 상태

팀원은개인Git브랜치와개인API계정으로개발한다. 현재서버배포는관리권한이있는찬원이SSM으로진행한다. 팀원의DBeaver접속권한을배포권한으로확대하지않는다.

서버에서 /opt/team8-shared-api/shared-components.sh status 로API·워커상태를확인한다. restart-worker는큐를먼저멈춘뒤워커재시작·준비확인·큐재개를수행한다. pause/resume은큐만제어한다. DB/Redis볼륨은보존된다.

로그는 docker logs --tail 100 team8-shared-api, team8-shared-worker, team8-shared-queue에서각각확인한다. 로그를공유하기전계정/개인정보를확인한다. /ready의queue=ok는Redis접속상태이므로별도로큐컨테이너의실행·재시작횟수도확인한다.

## 코드 배포 순서

1. 검토된커밋과대상파트를확정하고,기존이미지태그·설정·DB백업을확인한다. 데이터삭제·전체초기화를수행하지않는다.
2. 비밀파일/실데이터/node_modules를제외한소스를서버의새release폴더로전달한다. 백엔드는backend/Dockerfile,음성은voice/Dockerfile.mock으로새태그의이미지를만든다. 이목업워커Dockerfile은현재서버의기존백엔드이미지를기반으로한다. 개인환경은infra/Dockerfile.voice-local을사용한다.
3. 큐를먼저중지한다. 음성만교체하면기존워커컨테이너를중지·백업이름으로보존하고새워커를같은API네트워크공간·설정·접수볼륨으로실행한다. 준비확인후큐를재개한다.
4. API를다시만드는배포에서는워커·큐도먼저중지한다. 기존컨테이너를삭제하지않고백업이름으로보존한다. 새API를team8/team8-frontend-dev네트워크와기존runtime/api.env,127.0.0.1:18771,root-path/shared로기동한다. 워커·큐는새API의네트워크공간에다시연결해생성한다. API만교체하고오래된네트워크공간의워커·큐를그대로두지않는다.
5. 새컨테이너는unless-stopped·로그회전·메모리제한을유지한다. HTTPS의동적DNS대상이바뀌면nginx -t후reload하여새API주소를읽는다. 인증서와기존프론트용경로를보존한다.
6. health/ready/docs→회원가입/로그인→문의접수→실제워커접수/결과→completed를확인한다. 다른계정격리와기존서비스응답도확인한다.
7. 실패하면새서비스를중지하고보존한기존API·워커·큐를기존이름으로되돌려시작한다. 같은DB/접수볼륨을사용한다. DB구조가변경되는배포는별도검토된마이그레이션과복구절차가필요하다.

현재작업은위구성을실제설치했고워커·큐재시작후동작을검증한다. 새버전교체/복구전체자동화와모든팀원PC실행은검증완료로표시하지않는다. 실제음성서비스연동은현재목업과별도작업이다.
